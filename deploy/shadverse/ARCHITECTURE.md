# SHADVERSE JARVIS platform architecture

SHADVERSE ©

The Creator’s private assistant is the first deployment of the unified SHADVERSE JARVIS platform. The immediate launch uses the Phase 01 deployment at commit `732a354942a` and the official OpenClaw stable package. The commercial design extends that deployment through a shared product surface and a SHADVERSE control plane. This document specifies the future boundaries. The current branch ships the Creator profile and deployment tooling.

## Product and access

The product has one Persian-first, mobile-first application. Server policy decides which routes, actions and capabilities each signed-in user can use. The Creator starts with one private personal tenant. A personal tenant contains one member until collaboration is designed and approved.

| Access profile                | Authority                                                                                                                                                                                                  |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Creator / Super Administrator | Platform administrative role. The same person has a separately scoped member session for their private assistant. Platform role grants require explicit provisioning and fresh MFA for privileged actions. |
| Free                          | Member role with a configurable Free plan. The starting catalog uses approved zero-cost routes and hard limits.                                                                                            |
| Pro                           | Member role with a configurable Pro plan and monthly or annual terms.                                                                                                                                      |
| Ultra                         | Member role with a configurable Ultra plan and monthly or annual terms.                                                                                                                                    |

Model identity as `User`, `Tenant`, `Membership` and scoped role assignments. Model commercial access separately as `PlanVersion`, `Subscription` and entitlement grants. An upgrade cannot grant an administrative role. Membership and ownership checks precede plan checks. A commercial user can operate their own resources only. Platform administrators can administer accounts, plans and runtime health with aggregate usage data. Access to a private payload for incident response requires a separate time-limited grant, an explicit reason, and an audited access record.

## Runtime and data isolation

The future public surface is the SHADVERSE application and its authenticated product API. OpenClaw RPC, HTTP, WebSocket bootstrap credentials and operator tokens stay private. The backend derives tenant, user and runtime from the authenticated membership and a server-controlled runtime registry. A client-provided resource or runtime identifier is an object lookup key. It grants no authority.

- Give each personal user an independent OpenClaw Gateway runtime with its own unprivileged OS identity and isolated filesystem, process and network boundary. Keep the Creator runtime in a separate deployment and credential realm. Before commercial onboarding, demonstrate the boundary on the chosen substrate. Start commercial isolation with one VM or microVM per user unless equivalent isolation is independently verified. Shared hosts, where qualified, get no cross-user mounts, local sockets, service identities or secret access. Workspaces and agents are contained inside the assigned runtime.
- Give each runtime a private state directory, workspace, SQLite stores, attachment staging area, caches, indexes, worktrees, logs and backup namespace. Keep shell, elevated tools, automation, browser control and arbitrary egress disabled by default. Admit only documented OpenClaw operations through a narrow adapter. Runtime credentials stay server-side. Never forward a customer’s request directly as a privileged Gateway call.
- For shared platform metadata, bind every user-owned record to both tenant and owner at creation. Apply server-side authorization on all operations, tenant-aware relational constraints and database row policies as defense in depth. Bind short-lived download grants to one authorized object and action. Never rely on storage prefixes by themselves. Bind background jobs, event streams and caches to the same identity context, and recheck active access before a job starts or a stream resumes.
- Encrypt state, object data and backups at rest and use TLS in transit. Put provider secrets in independently scoped secret storage with rotation and access auditing. Restore only into an unused isolated destination, validate owner and runtime bindings, and rotate or reissue credentials as needed. Lifecycle policy covers replicas, staged uploads, caches and backup expiration. Keep private artifacts, customer identifiers, credential dumps and deployment configuration containing secrets out of GitHub.
- In the first commercial pilot, use synthetic two-user fixtures to verify both the product authorization layer and the runtime boundary. Include read, write, search, streaming, attachment download, galleries, projects, backup restore and credential separation. Also verify that single-user recovery preserves the other user’s state.

## Creator and commercial model access

**Creator.** The approved Phase 01 route is Codex device-code OAuth using the pinned OpenClaw release’s embedded runtime. Codex browser OAuth and eligible Sign in with ChatGPT are alternatives under the same Creator-only boundary. Pair only Creator devices via loopback, SSH or the documented private tailnet. OAuth tokens and the Gateway token remain in the Creator runtime. The commercial system has no mount, vault grant, application route or fallback to this runtime. [Pinned OpenAI authentication](https://github.com/openclaw/openclaw/blob/v2026.11.10/docs/providers/openai/authentication.md)

**Commercial.** Product sign-in authenticates the person to SHADVERSE. A separate internal AI Gateway selects and calls providers with commercial service credentials and sends requests only after entitlement and budget checks. Use a server-managed catalog of explicit routes with provider, model, input capabilities, approved tenant population, availability, terms review, and pricing version. Store a user’s preferred route as a catalog ID and intersect it with current authorization on every turn. A provider adapter receives the least privilege necessary. Runtime egress and short-lived service credentials enforce the gateway route. Prototype a documented OpenClaw provider interface against a synthetic provider before adopting it. Use approved local or legitimate free-to-use routes first. Any paid provider, chargeable fallback or paid checkout requires separate Creator authorization. When the eligible route set is empty, show a clear unavailable state.

## Registration, plans and usage

- **Persian Gate and registration.** The first screen is Persian RTL and offers sign-in and registration-code activation. Use one-time, high-entropy codes stored as digests, with expiration, rate limits, revocation, and optional binding to a verified identity or invitation. Require a verified account, then consume the code and activate membership in one transaction. Keep the code separate from authentication and from role assignment. The Creator is provisioned through an administrative path.
- **Plans and periods.** Version feature keys and limits in a server-owned catalog. Example keys include allowed model routes, attachment limits, memory capacity, voice, project slots and token allowance. Model paid terms as monthly or annual with explicit effective, current-period end and renewal dates. Keep billing cadence independent of quota reset cadence. Derive effective entitlements from current plan version, documented overrides, account and subscription state, and emergency policy. The application renders the returned entitlement state and every protected API enforces it independently.
- **Lifecycle.** Represent pending activation, active, expired, suspended and revoked access. A scheduled cancellation retains access until period end when policy allows. Upgrade applies at an explicit effective date and renewal extends an authenticated subscription term. Suspension blocks new work and protected access according to policy. Revocation invalidates access grants and cancels or contains queued and active work. Process trusted billing events idempotently and handle out-of-order events through reconciliation. Test the lifecycle with manual grants or a simulated billing adapter before enabling any checkout.
- **Accounting.** Issue one idempotency key per customer request and a unique ID per provider attempt. Atomically reserve quota and maximum allowed spend before dispatch, including concurrent requests and fallback attempts. Settle against measured input, output, cached and other provider-specific units. Record unknown usage explicitly and reconcile reservations against provider receipts. Version pricing and currency and retain provider, model, request, attempt, tenant and user attribution without prompts or attachments. Report measured, estimated and billed values separately. Fail closed when an applicable hard cap cannot be enforced. Creator subscription estimates stay outside commercial ledgers and budgets.

## Central administration and emergency response

Use the same product shell with an independently authorized administration surface. Provide controls for tenants, users, registration-code issuance and revocation, plan versions, entitlement overrides, route approvals, quotas, cost reports, suspensions and runtime health. Keep administrative actions separate from assistant chat tools and use step-up authentication for privileged changes.

Record actor, target tenant, resource, action, outcome, timestamp, and a correlation ID in a restricted append-only audit sink. Include policy changes, evidence of provider dispatch, privileged reads, exports and restores. Keep tokens, registration codes, message bodies and uploaded content out of routine audit events. Document retention and access policies before accepting customer data.

The emergency switch can disable all commercial inference or target a tenant, user, provider or model. Enforce it both at product admission and at the AI Gateway, including queued jobs, retries and fallback. Revoke affected grants and cancel active dispatch or streams where supported. Account for requests already accepted by the provider. Keep the Creator’s independent assistant available unless an operator explicitly invokes its own shutdown path. Audit switch activation and recovery. Require explicit administrative release and exercise the procedure against synthetic traffic.

## Phase 01 corrections and launch decisions

| Phase 01 assumption                          | Corrected interpretation                                                                                                                                                                  |
| -------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Dedicated single-user product                | Dedicated first runtime of the unified platform. Its service, initializer, state layout, stable pin and preserved tests support the Creator launch.                                       |
| Private dashboard as the product entry point | Keep it as the Creator’s initial private UI. The future shared UI owns product authentication, activation, plans and administration. Direct Gateway access stays private.                 |
| Local identity and permissions               | The Phase 01 token and OpenClaw pairing authenticate the Creator’s device to one Gateway. Future product RBAC and entitlements are separate checks enforced outside the runtime.          |
| One local state tree and personal OAuth      | Preserve the Creator’s state and credential realm as-is. Provision independent state and credentials for every commercial user and enforce that isolation at the host and service layers. |
| Upstream usage and feature views             | Reuse their diagnostics for the Creator. Commercial billing and entitlements use centrally enforced limits and independently reconciled records.                                          |

## Phased roadmap

1. **Creator launch after approval.** Deploy the existing profile to the approved private host, check Gateway readiness, then let the Creator complete device-code consent. Verify the subscription route, a real reply, restart persistence, and a verified backup. Pair the Creator’s phone through private HTTPS if requested. Keep paid APIs inactive. The deployment commands are in the [Phase 01 runbook](README.md).
2. **Prove commercial isolation.** Build a thin Persian Gate and product authentication flow, basic tenant membership and roles, activation codes, a runtime registry and one narrow OpenClaw adapter. Provision two isolated synthetic users. Require authorization, storage, network and secret-separation checks before accepting any external users.
3. **Pilot Free.** Use an approved no-cost catalog, enforce routing, usage reservations and hard limits, and exercise administration, audit, backup and stop controls. Build only the product screens and operations needed for the pilot.
4. **Add Pro and Ultra after approval.** Introduce versioned offers and a sandbox billing adapter first. Demonstrate idempotent upgrade, renewal, cancellation, suspension and revocation, and reconcile usage. Obtain explicit approval before enabling billing or a paid provider.

## Verification and limits

The Phase 01 commit records a full source build, 116 targeted tests, and 21 Chromium tests. It records one inconsistent video-gallery case that passed on isolated rerun. The stable-package smoke test verified loopback authentication, terminal denial, restart persistence for synthetic data, verified backup and staging restore, and Persian RTL at 390 px. Its audit reported zero critical findings, a loopback proxy advisory and a limited deep probe. These are Phase 01 results for one isolated runtime. For this correction, the existing checkout was checked against Phase 01 and the architecture was reviewed against OpenClaw’s trust, scope, persistence, UI and provider documentation. The architecture change adds documentation only. Production host startup, mobile ingress, Creator sign-in and live inference still need the approved host and Creator consent. The commercial isolation and billing acceptance checks above are future implementation gates.
